# Steam Frame VR port status

The [README](../README.md) covers the current features, controls and confirmed play results. The detailed checks and measurements below retain their original development context.

This branch adds a ROM-free, ARM64 Steam Frame build of the existing Quest OpenXR/GLES3 port. The Frame code is opt-in with `TCVR_STEAM_FRAME`; the default CMake and manifest paths remain the Quest build. The package id is `org.timecrisis.frame`. Its immersive activity uses Khronos OpenXR launch metadata and includes the Android OpenXR loader. It does not declare Meta device features.

The game renderer, camera projection, aim calculation, sRGB negotiation, model, and approximately 59.906 Hz arcade simulation remain on their established paths. Frame defaults to separate eye passes. `frame-display.cfg` may set `multiview=1` to compare the optional OpenXR multiview path and `eye_resolution=512..2160` to set the target maximum dimension per eye. The recommended aspect ratio is preserved while scaling up or down to that target, then clamped to the runtime's per-eye maximum; the recommendation, maximum, target, and actual size are logged. Frame does not request a display refresh rate; the XR loop follows `predictedDisplayPeriod`. Quest keeps its existing refresh negotiation.

Frame immersive gameplay now defaults to the approved Large window: `gameplay_scale=1.6` expands reconstructed X/Y and the live HUD plane by 60% at fixed Z, using the source focal length divided by scale. Source 640×480 coordinates and off-center camera origins remain intact. The same effective camera drives polygons, nearest-surface lookup, authored-depth billboards, shot marks, native hit/fallback aim and the guide. Runtime eye FOV, IPD, poses, head rotation and simulation are unchanged. This is an apparent-window adjustment: geometry becomes wider/taller at the same depth, changing physical proportions and relative parallax; it is not a uniform physical-world scale. Flat desktop and the separate pause/options panel keep their existing projection.

The full rectangular cyan guide remains centered on the 640×480 boundary: 5-native-pixel dark (#10191b, 80% alpha) backing and 2-native-pixel cyan (#72d5e8, 85% alpha) stroke. Outside that live-camera plane at 2.5 m, a black overlay defaults to `outside_darkening=0.65`. A single full-eye triangle uses actual per-eye inverse transforms to leave forward intersections inside the plane clear. It covers the entire exterior, including side/rear views and head translation, without overlapping corner alpha or finite surround edges. The mask and guide follow world color processing, before laser/gun, and are absent in flat view, pause and the color probe. The border is a HUD-plane cue: native hit tests still use actual world surfaces, so depth and translated eye/controller origins can move shootability relative to that plane.

Both settings load at startup from persistent `frame-display.cfg`: scale is clamped to 1..2 and darkening to 0..1; missing, malformed or nonfinite values use defaults. Loading does not rewrite the file or alter other keys. Use scale 1 for the previous dimensions, 1.35 for Roomier, or 1.6 for approved Large; darkening 0 disables the surround. Startup logs the applied values. The current build is installed and has been played on the Frame at 2160×2160 per eye and a 120 Hz display setting. The cyan frame grew from approximately 1023×768 to 1637×1230 pixels, covering 75.8% of the eye width. Gameplay remains bright, the exterior is dimmed, and the angled aperture follows the game plane. The larger window and surround were accepted in a normal Steam play session: “Looks good; finished and quit.”

The Steam launcher's first-run activity imports `timecris.zip` directly from `/sdcard/Documents/TimeCrisisVR`. It verifies the ROM chips by SHA-256 and accepts renamed chip entries. Storage access is tested by creating and deleting a unique probe in that root; Android storage settings are offered only after a real read/write failure. The extracted chips live in `roms/`; the checked-in gun model is copied to `models/`. The native process changes its working directory to this same persistent root before opening the game. Settings, logs, diagnostic requests, captures, and game replay files therefore remain outside the app cache and survive Lepton resets.

Frame controls use fixed physical sides even when the saved default weapon hand changes. Either trigger selects that hand and fires; either squeeze/value holds the virtual pedal. Releasing both grips hides behind cover and reloads. Right A adds credits, right B toggles the laser, and right Menu pauses or resumes. Left View returns from options on a short press, recenters after 1 second, and recenters plus recalibrates upright height after 3 seconds. A hold does not also trigger the short action. In options, right X switches between grip and physical ducking, the right thumbstick adjusts gun angle from -60 to +60 degrees, its click changes the default hand, and left-stick click resets the angle.

The Valve Frame controller profile is suggested only when `XR_VALVE_frame_controller_interaction` is available; OpenXR Touch is the fallback. Touch controllers do not expose the Frame left View or right X controls through this profile. On that fallback, left X recenters immediately, left Y changes cover mode in options, and left Menu pauses; the 1-second and 3-second View gestures are unavailable. Right A/B retain their fixed credit/laser roles.

For unattended Frame diagnostics, place a one-shot `vrdiag.once` text file in the persistent root before launch. It is parsed once and renamed to `vrdiag.last`. Boolean keys accept `0` or `1`: `force_render`, `synthetic`, `synthetic_hands`, `autostart`, `colorprobe`, `dump_eyes`, `dump_hud`, `timing`, `pose_report`, `grip_anchor`, and `sprite_report`. Numeric keys are `diag_yaw` and `diag_hand_yaw` in degrees, `autostart_tick` (simulation ticks, default 600 for autostart and clamped to 1,000,000), `probe_seconds` (clamped to 60), `dump_tick` (simulation ticks, clamped to 1,000,000), and `self_exit_seconds` (clamped to 120). `dump_tick=0` captures on the first rendered frame; a positive value delays eye and HUD dumps until `ss22_input_update` has advanced that many ticks during normal play. During diagnostic replay, readiness follows the recorded arcade `rr_frame` instead. This permits separate-eye and multiview captures at the same game state. `colorprobe=1` defaults to a 3-second probe; the left and right eyes render red and blue. With `force_render=1`, the one-shot path renders and advances the game while the headset is unfocused or the runtime says not to render, and records timing instead of resetting it. `autostart=1` holds the synthetic pedal to leave cover, waits for the first accepted simulation update at tick 600 by default, emits three credit pulses, waits 36 simulation ticks, then fires for 12 ticks. `autostart_tick` selects another start tick (0 means the first accepted update). This deterministic delay lets the arcade machine finish booting without using wall-clock timing; the selected tick and actual start are logged. Set `synthetic_hands=1` to render a visible gun hand and `diag_yaw` to set the diagnostic head yaw. Synthetic eye IPD rotates with that yaw; its view origin stays upright and does not cancel the requested yaw. Set `pose_report=1` to log `[vr-pose]` samples at most once per second per active controller hand while the app is focused. The report identifies the active Frame or Touch profile, physical sample hand, selected weapon hand, gun pitch, raw local-space aim and grip poses with validity flags, grip-to-aim translation and angular difference, and the rendered gun/muzzle/ray target. The report uses the real OpenXR pose actions and predicted frame time; synthetic hands are labeled as the render source and are never presented as live pose samples. `grip_anchor=1` enables a one-shot experimental comparison, off by default: a valid live grip position becomes the gun model pivot while aim pose still supplies orientation. Invalid or unavailable grip pose falls back to the current aim-origin placement. Synthetic hands skip the grip anchor; pose reports label the effective anchor (`aim`, `grip`, `aim_fallback`, or `synthetic_hands`) and its source. The experiment does not change barrel direction or gun-pitch math. `sprite_report=1` pairs one `[vr-sprite]` report with eye dumps on the first rendered frame at or after `dump_tick`; it automatically enables `dump_eyes` and disables a simultaneous color probe. The report header records the eye-1 scene frame and simulation tick, plus effective mixer background/fog/polygon-fade/screen-fade values after gun-flash filtering. `mixer_valid` reports whether those values are usable; `screen_fade_active` follows the renderer's valid-state, flag-bit and nonzero-factor gate, so a stored fade colour alone does not imply a drawn flash. One line per active sprite records its index, tile and z-sort fields, bounds, `prioverchar`, current projection classification, applied impact depth, and nearest reconstructed polygon depth/zsort/order (or none). It is emitted only after both eye dump files are successfully written, from eye 1’s cached scene. Each eye-capture log carries its own scene-frame/tick identity; the report uses eye 1’s scene and tick. `dump_eyes=1` writes `vr-dumps/vr-eye0.ppm` and `vr-dumps/vr-eye1.ppm`; `dump_hud=1` writes `vr-dumps/vr-hud.ppm`. The production `capture.request` marker is latched before an eye pair and consumed only after both captures succeed; a failed pair retries on a later rendered frame. Without a ready one-shot dump it writes `eye-0.ppm` and `eye-1.ppm`; with ready `dump_eyes` it writes `vr-dumps/vr-eye0.ppm` and `vr-dumps/vr-eye1.ppm`. With `sprite_report=1`, a latched marker also triggers the report and paired diagnostic eye dumps before `dump_tick` is reached. Frame timing summaries appear in `timecris-vr.log`. No diagnostic records image or audio continuously.


For deterministic replay of a saved train session, copy it to `vrdiag-replay.inputs` and create the empty marker `vrdiag-replay.once` in the persistent root. Startup validates the `SS22REC 1 TC` header and full EEPROM image before consuming the marker or selecting `--replay`. Missing or malformed input stops startup while preserving the marker, replay source, and latest/previous session recordings. A valid replay skips input-recording rotation and creation, and does not initialize external EEPROM persistence; the recording remains authoritative for arcade inputs and gun coordinates. Later `vrdiag.once` settings still control rendering and the target dump tick. Neither the marker nor replay recording is included in the APK or delivery bundle.

## World-effect sprite placement

On Frame, `quest_scene.c` reconstructs ordinary layer-1 sprites at their authored low-21-bit depth divided by `qvr_units_per_meter`. The game's TS2 Ver.B routines at `0x10E12` and `0x10EDE` subtract the camera position and rotate the actor; `0x10E48`/`0x10F12` add `0x200000` to positive camera Z and store it at actor offset `0x8C`. The VICS emitter copies this field at `0x10C26`/`0x10C2A`. These paths are visible in the pinned upstream `timecris/gen/tc_lifted_00.c`; no translated game source or ROM inputs are added to this repository.

This is an authored depth estimate. Some callers subsequently bias the value for painter priority (for example `0x5BF4` subtracts `0x1800`); it is not an exact physical position for every effect, and polygon sort keys cannot be inverted to obtain one. The correction changes only billboard vertices, preserving the game's shared sprite/polygon draw order, pixel colours, transparency and screen fades. It does not add depth testing or put sprites into aiming/collision geometry. Each billboard retains its original rectangle when viewed from the arcade camera; both eyes and head motion then use the world transform.

The rule requires reconstructed world geometry in the current scene and a finite positive world scale. Low depths through `0x10` (the upstream Time Crisis HUD cutoff), other priority layers, and the saturated `0x1FFFFF` endpoint keep the flat path. Scenes without world geometry, the flat desktop view and the Quest build keep their previous behavior. Shot marks retain their existing nearest-surface projection. Preparation adds constant work per cached sprite and no new polygon scans, grid construction or allocations. Sprite reports distinguish `world_authored_depth` and expose `projected_depth_m`; `impact_depth_m` remains specific to shot marks.

Host production-path checks cover both build flags, world scale, off-centre rectangle preservation, depth-dependent stereo disparity, stale cache rejection, HUD/layer/title exclusions, unchanged polygon aiming and screen-fade reporting. The installed build `3e60774` produced inspected, matched 2160-square quiet-scene eye captures preserving the HUD and calibrated shot marks; these captures contain no active world-effect sprite. The wearer then reported that the explosions look great, accepting the correction subjectively on the headset. Matched active-flame A/B images remain unavailable, and a full-screen yellow flash is not evidence of world-sprite quality.

## Build and acceptance

Build on the configured macOS host with:

```sh
sh Build-Steam-Frame.sh --rom /path/to/timecris.zip --jobs 4
```

The script verifies the pinned SDL and OpenXR archives, copies the exact upstream submodule commit to an ignored disposable tree before applying source patches and generated game code, and keeps the signing key outside the repository and build cache. It writes `artifacts/TimeCrisisVR-SteamFrame-arm64.apk` and a matching `TimeCrisisVR-SteamFrame-build-info.json`. The APK contains no ROM archive, extracted ROM chips, generated game source, or signing key.

Source, native build, Java packaging, APK signature/alignment, manifest, ABI, and portable production-path tests can be verified on the host. They do not prove Steam launch, controller firmware bindings, storage permissions, rendered headset output, color response, or comfort. Those require the Frame acceptance run. Start with the persistent-root importer and one-shot diagnostic above, then check focus loss/re-entry, both triggers and grips, fixed-side buttons, short/held View behavior, the options labels, eye/HUD dumps, and the default separate-eye renderer while worn.

## Foveation investigation

[Valve documents runtime foveation and eye tracking](https://partner.steamgames.com/doc/steamhardware/steamframe/engines/custom?l=english). Current app logs show GLES through Zink/Turnip and Valve FDM injection layers loaded; that does not prove active foveation or a performance benefit. The app does not request game-controlled foveation profiles. An optional future comparison needs CPU/GPU separation and repeated same-scene on/off runs at 2160-square resolution, including HUD and aiming sharpness. No foveation feature or default has been implemented in this milestone.
